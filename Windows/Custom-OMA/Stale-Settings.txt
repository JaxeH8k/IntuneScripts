The short answer: they shouldn't just be ignored, because ADMX-ingested settings tattoo in a way that's functionally meaningful — but the best practice is to prevent the orphaning in the first place through removal ordering, and only do registry cleanup when you're already stuck.
Why they linger
Built-in ADMX-backed policies via Policy CSP are designed to be non-tattooing. Ingested ADMX is different: the settings ultimately land as registry values in the location the ADMX defines (typically under HKLM\SOFTWARE\Policies\<Vendor>\... or wherever the ADMX's key attribute points), and the application reads those values directly. If the removal doesn't process cleanly, those values stay behind and the app keeps honoring them. So a "lingering" ingested setting isn't cosmetic residue — it's still enforcing behavior with no policy backing it. That's the argument against ignoring them.
The most common cause of orphaning is ordering: if the ADMX ingestion policy (the ADMXInstall OMA-URI) is removed or unassigned before the setting policies that depend on it, the client loses the ability to interpret and unwind those settings, and they tattoo. Same thing happens if a device is offline/retired-and-reimaged mid-removal, or if the profile is deleted while devices haven't checked in.
Best practice

Removal order matters. Unassign the individual setting policies first, let devices check in and confirm the settings are gone, and only then remove the ADMX ingestion policy. Treat the ingestion policy as a dependency with a deprovisioning gate, not something you delete in the same change window.
Prefer "set to disabled/default, then remove" over straight deletion for settings you know tattoo badly. Pushing an explicit disable first forces the client to write the neutral state, so even if the later removal misbehaves, the tattooed value is benign.
For already-orphaned devices, clean up with a Remediation (detection + remediation script) rather than manual intervention — at your device count that's the only sane vehicle. Target the application-facing registry values the ADMX controlled (the HKLM\SOFTWARE\Policies\<Vendor>\... keys). Detection should check for the value existing while confirming the corresponding Intune policy is no longer assigned to that device's groups — otherwise you'll fight the MDM client rewriting it.
Avoid surgery on the MDM bookkeeping keys. The ingested ADMX metadata lives under HKLM\SOFTWARE\Microsoft\PolicyManager\ADMXInstalled and ADMXDefault (<VERIFY_THIS> — confirm exact key names/structure for your OS builds before scripting against them). Editing those by hand is unsupported and can desync the PolicyManager state; if that state is corrupted, the supported-ish path is re-ingesting the ADMX and re-sending the settings so the client can process a clean removal, or worst case an MDM re-enrollment/sync reset. Stick to cleaning the app-facing keys and leave PolicyManager alone unless you have no other option.
Decide per-setting whether stale = harmful. If the tattooed value matches your desired steady state anyway (e.g., a hardening setting you'd keep regardless), it's reasonable to deprioritize cleanup and just document it. If it blocks functionality, conflicts with a successor policy, or shows up in compliance/audit scans, remediate.

One more thing worth doing at your scale: audit which of your ingested ADMX settings even still need ingestion. Microsoft has steadily moved third-party and Windows settings into the Settings Catalog, and migrating off custom ADMX ingestion where possible eliminates this whole class of problem — Settings Catalog removals behave much more predictably.
